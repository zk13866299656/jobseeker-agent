# 切片4（上下文压缩）端到端测试记录

日期：2026-08-13
被测功能：`chat_message.msg_type` 三态标记 + 手搓 `ContextCompressor` 滚动摘要

## 测试目标

验证上下文压缩四个关键点：

1. **触发**：normal 消息字符总数超 8000 时自动触发压缩。
2. **摘要**：LLM 生成滚动摘要，保住关键事实、忽略无关内容。
3. **归档**：早期原文标记 `archived`（不删），最近 10 条保留 `normal`。
4. **摘要独立回忆**：早期原文被归档后，模型仍能靠摘要回忆起早期内容。

## 测试方法：SQL 灌数据模拟长对话

**问题**：手动聊到 8000 字太繁琐、也不可控（没法精准顶到阈值）。

**方案**：触发条件只认 `chat_message` 表里 `msg_type='normal'` 消息的字符总数，所以直接往最新会话里插入填充消息，精确把字符数顶过阈值（8000）+ 消息数顶过保留窗口（10），再发一条真实消息触发压缩。

```sql
INSERT INTO chat_message (session_id, role, content, msg_type)
WITH RECURSIVE seq(n) AS (
  SELECT 1 UNION ALL SELECT n+1 FROM seq WHERE n < 20
)
SELECT '<session_id>', 'user',
       REPEAT('这是一段撑长对话的填充文本，与求职规划无关。', 20), 'normal'
FROM seq;
```

## 测试步骤与结果

### 步骤1：造一个「带事实」的真实开头

浏览器新建会话，发一句带真实事实的话（用于后续验证摘要回忆）：

> 我叫王小明，目标是 Java 后端工程师。

产生 id 27（user）、id 28（assistant，回答里含三道 Java 面试题）。

### 步骤2：灌 20 条填充消息

执行上面的 SQL 灌入 20 条 normal 填充消息。

结果：会话 normal 字符总数 **9032**（> 8000 阈值），normal 消息 **22 条**（> 10 保留窗口）。

### 步骤3：发「继续」触发压缩

回答结束后，`AgentLoop` 末尾的 `compressIfNeeded` 自动触发压缩。

结果三态分布：

| msg_type | 条数 | 字符数 | 含义 |
|---|---|---|---|
| archived | 14 | 5512 | 早期原文（含王小明、面试题），不再喂模型 |
| normal | 10 | 3707 | 保留窗口内的最新原文 |
| summary | 1 | 295 | 滚动摘要（~300 字内） |

### 步骤4：验证摘要质量

摘要内容（295 字）：

- 准确保住「王小明，目标岗位为 Java 后端工程师」；
- 正确识别 20 条填充文本为「与求职规划无关的填充文本」，**没当事实**；
- 忠实记录三道面试题（HashMap 底层原理 / JVM 内存模型 / == 与 equals 区别）。

### 步骤5：验证摘要独立回忆（核心）

问：

> 你之前给我出过哪些 Java 面试题？

模型答对三道题，且思考里明确写：

> 「根据对话摘要，我之前提供过 Java 基础高频面试题（HashMap 底层原理、JVM 内存模型、== 与 equals 区别）」

**结论**：这三道题的原文已归档、不再喂给模型，模型纯靠摘要回忆——证明压缩摘要确实独立保住了早期内容。

## 发现的问题：记忆串台

**现象**：步骤3 的回答里，模型突然说「你已决定转向 AI 方向」，与「王小明想找 Java 后端」矛盾。

**定位**：查 `user_memory` 表，发现一条旧的 `fact: 转向AI方向`——是切片3 用「张凯」测试时留下的，未随人设更换而清理。

**原因**：`fact` 是「其他」兜底类型，会累积事实；用户换人设时 `name`/`target_role` 会覆盖更新，但旧 `fact` 不会自动清，可能和新目标矛盾。

**修复**：删除陈旧 `fact` 后，模型正确回答「王小明 / Java 后端工程师」。

（此发现已记入复盘疑难点清单第 6 条。）

## 结论

切片4 上下文压缩 E2E 验证通过：**触发、摘要、归档、摘要独立回忆** 四项全部符合设计。原文全保留（`archived` 不删），前端仍可回看完整历史。
